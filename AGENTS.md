- Keep restaurant menu content centralized in `src/lib/menu-data.ts` so filters, cards, and details never drift.
- Keep menu category IDs compatible with homepage hash links and use the shared cart store for menu selections so navigation never loses the order.
- Orders are stored in the `public.orders` table (Lovable Cloud) with realtime updates; `src/lib/order-store.ts` keeps localStorage only as instant cache/fallback — never reintroduce localStorage as the source of truth for order status.
- Orders are created only by the server function `placeOrder` (`src/utils/orders.functions.ts`): the browser sends just menu refs, quantities, time and contact, and `checkOrder` in `src/lib/order-rules.ts` rebuilds names, prices, delivery fee, total, pickup time (Europe/Berlin) and order number from the menu — never insert into `public.orders` from the browser and never trust a price, total, `paid` or status sent by a client. Every rule in `order-rules.ts` has a test in `order-rules.test.js`.
- Online payments use Stripe Embedded Checkout with dynamic `price_data` line items built by `createOrderCheckout` from the stored order (order number + guest `access_token` only; menu prices already include VAT) — never create static Stripe products per menu item, and never let the browser choose line items, return URL or the Stripe environment (test/live comes from the build's `VITE_PAYMENTS_CLIENT_TOKEN` via `src/lib/payments-env.ts`). The kitchen only shows online/PayPal orders after the webhook at `src/routes/api/public/payments/webhook.ts` marks them `paid`; it does so only when the paid amount equals the stored total and answers 500 on database errors so Stripe retries. In a live build, payments from Stripe test mode never count as paid (`fromRow`).
- Admin access (`/admin` dashboard, `/kitchen`) requires Supabase Auth plus a confirmed email listed in `public.admin_emails`; the database function `public.is_admin()` is the single source of truth and also guards RLS — never gate admin data only in the UI.
- Guests read their own order only through the server function `getGuestOrder` (`src/utils/orders.functions.ts`) with the per-order `access_token` stored on their device; `anon` has no rights on `public.orders` at all and the team may only update `status` (`supabase/sql/0009_server_side_orders.sql`) — never grant more.
- Menu interactions are logged anonymously to `public.menu_events` via `src/lib/analytics.ts` (no names, contacts, IPs or cookies); the dashboard reads them only through `public.admin_menu_analytics()`. SQL changes live in `supabase/sql/`.
- `/admin` and `/kitchen` are installable home-screen apps (iOS/Android) via `appHead()` in `src/lib/app-install.ts` and `public/app/*.webmanifest`; there is deliberately no service worker, so new deployments are never served stale.
- Sold-out items/options (`public.menu_availability`) and the online-order pause (`public.shop_status`) are enforced by the `orders_check_available` trigger (`supabase/sql/0003_availability.sql`); `src/lib/availability.ts` only mirrors them in the UI — keep keys as `item:<menu name>` / `option:<option value>`.
- Page imagery comes from the shop's own product photos in `src/assets/brand/` (cut-outs from the shop's digital menu, plus one real shop photo); `hero-bowl.jpg` is reserved for the homepage hero — never use third-party/customer photos.
- Delivery partner logos (`src/assets/partners/`) are the only third-party artwork allowed, and only on the "Bestellen bei …" buttons: official files only (Wolt: press kit on press.wolt.com; Lieferando: official logo supplied by the owner, house mark cropped and centred on its own #FF8000 background), used unaltered (no recolouring, rotating or effects); colours come from the `--lieferando` / `--wolt` tokens.
- Legal pages (`/impressum`, `/datenschutz`, `/agb`) are drafted only from official sources (statutes on gesetze-im-internet.de, DSGVO as published by the BfDI, notices of the EU Commission and the Hessian data-protection authority) — never from third-party templates or generators; each statement carries its legal basis in a code comment. Owner-specific facts live only in `src/lib/legal-info.ts` (`null` = still open, shown as a red placeholder); never publish while `isLegalComplete()` is false. The order button must read "Zahlungspflichtig bestellen" with nothing else on it (§ 312j Abs. 3 BGB), for every payment method. Fonts are self-hosted in `public/fonts` — never load Google Fonts from Google; never store analytics IDs on the device (§ 25 TDDDG).
- Menu photos live as real files in `src/assets/menu/*.webp` and are imported directly so Vite bundles them; never reference them via Lovable `*.asset.json` pointers (`/__l5e/assets-v1/…`), which only resolve on Lovable hosting.
- "Meine Bestellungen" works without accounts: the device keeps its per-order guest tokens; `useMyOrders()` / `ActiveOrderPill` read live status only via `getGuestOrder` and merely cache it with `orderStore.remember()`.
- Admins change their own email/password in "Konto & Sicherheit" (`src/components/admin/account-sheet.tsx`, current password re-checked); the `on_auth_email_change_transfer_admin` trigger (`supabase/sql/0004_admin_email_change.sql`) moves the `admin_emails` entry (with role and stats right) to the new address once Supabase confirms the change.
- Team & Rechte (`src/components/admin/team-sheet.tsx`, owner only): `admin_emails.role` (`owner`/`staff`) and `can_view_stats` are changed only via `public.owner_set_access()`, and accounts are created only by invitation (`inviteTeamMember` in `src/utils/team.functions.ts`); the `before_auth_user_insert_require_invite` trigger (`supabase/sql/0006_team_roles.sql`) blocks self sign-up. Statistics (`admin_menu_analytics`, `menu_events`, order history older than 7 days) require `public.can_view_stats()` — never re-add a sign-up form or gate statistics only in the UI.
- Hosting moves from Lovable to Vercel: `vite.config.ts` builds the Vercel output when `VERCEL` is set (inside Lovable the Lovable config keeps its own target). Every environment variable Vercel needs is listed in `.env.example`. A new Supabase project is set up by running `supabase/setup.sql` once; it is generated from `supabase/sql/0*.sql` by `sh supabase/build-setup.sh` — rerun that after every SQL change, and keep every SQL file idempotent (the setup runs twice without errors).
- Stripe and Resend work two ways (`src/lib/stripe.server.ts`, `src/lib/email.server.ts`): a real key (`sk_test_…`/`sk_live_…`, `re_…`) talks to the provider directly (Vercel); anything else is a Lovable connector key and goes through the Lovable connector gateway with `LOVABLE_API_KEY`. A Stripe test key is refused for live payments and vice versa.
- Emails go through Resend (`src/lib/email.server.ts`, secret `RESEND_API_KEY`, plus `LOVABLE_API_KEY` only on Lovable, sender domain `yamiin-jaiyanas.de`); designs live in `src/lib/email-templates.ts`. Order confirmations are sent once via `deliverOrderConfirmation()` (onsite right after ordering, online/PayPal only once the webhook marks them paid; `orders.confirmation_sent_at` dedupes). Team mails (invite, password reset, email change) use `auth.admin.generateLink()` server-side and are sent by us, rate-limited via `public.auth_mail_log` — never fall back to Supabase's default auth mails or call Resend from the browser.
